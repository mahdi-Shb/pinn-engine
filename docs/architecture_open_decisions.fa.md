این یادداشت حاصل گفت‌وگوی طراحی است؛ توصیف API فعلی PINNlab نیست. تاریخ شروع: ۲۰۲۶-۱۰-۱۲.

## پایهٔ مورد توافق

- «کمیت» یا Quantity تعریف یک چیز مانند دما، فشار یا مختصات است؛ از مقدار فعلی آن جداست.
- شکل Quantity شکل یک مقدار است و محور نقاط/batch را شامل نمی‌شود: اسکالر مانند T برابر ()، بردار سه‌بعدی برابر (3,) و تنسور تنش سه‌بعدی برابر (3, 3) است.
- هویت Quantity بر اساس (geometry، نام) تعیین می‌شود؛ کاربر می‌تواند چند شیء Quantity جدا برای همان کمیت تعریف کند و لازم نیست یک شیء مشترک را همه‌جا نگه دارد.
- شکل جزئی از کلید هویت نیست؛ تعریف‌های یک هویت باید شکل سازگار داشته باشند. تعریف همان نام روی همان geometry با شکل متفاوت باید خطا بدهد.
- دو کمیت متفاوت روی همان geometry باید نام متفاوت داشته باشند؛ مثلاً T_pred و T_ref.
- یکسان‌بودن کلاس geometry برای یکسان‌بودن دو geometry کافی نیست. قرارداد دقیق شناسایی دامنه هنوز باز است؛ همان شیء geometry به‌عنوان قاعدهٔ سادهٔ اولیه پیشنهاد شده و قطعی نشده است.
- جهت اولیهٔ جدید برای هویت geometry: کاربر همان شیء geometry را در تعریف‌های مرتبط دوباره استفاده کند. وجود ID صریح و نیاز احتمالی config به آن، هنگام طراحی نوشتار config بررسی شود.
- tensor فعلی، نسخهٔ نتیجه و cache داخل تعریف Quantity قرار نمی‌گیرند.
- قرارداد پایهٔ مورد توافق برای جزء محاسباتی: نگاشت Quantity به مقدار را ورودی بگیرد و نگاشت دیگری را خروجی بدهد. نام Model پیشنهاد شده است.
- هر بخش باید فقط درخواست‌های مصرف‌کنندگان را پاسخ دهد و می‌تواند روش اجرای داخلی خودش را انتخاب کند.
- بررسی تغییر ورودی‌ها باید محلی باشد: هر بخش ورودی‌های مستقیم و وضعیت داخلی خودش را می‌شناسد؛ لازم نیست جزئیات داخلی تولیدکنندهٔ ورودی را بداند.
- اتصال سری و شاخه‌ای مدل‌هایی که روی یک دامنهٔ هندسی کار می‌کنند، خودش می‌تواند یک Model باشد؛ برای نمونه T(x, y, pc) = branch(pc) · trunk(x, y)، با عمل ترکیب مناسب خروجی branch و trunk.
- هماهنگ‌کنندهٔ مدل‌های محیط‌های متفاوت در multi-medium را فعلاً Model نمی‌نامیم؛ با ترکیب مدل‌ها روی یک دامنه فرق دارد. (این تصمیم موقت است؛ اگر بعداً محدودکننده یا نامناسب بود، بازبینی می‌کنیم.)
- geometry encoder آموزش‌پذیر یک Model در بخش PINN است؛ می‌تواند point cloud را ورودی و نمایش هندسه را خروجی بدهد. این تصمیم به معنی نهایی‌شدن ساختار داخلی بسته‌ها نیست.
- هر Model باید Quantityهای ورودی و خروجی خود را معرفی کند.
- Model می‌تواند پیش‌بینی، تبدیل داده یا تجمیع را انجام دهد؛ محاسبه‌کنندهٔ loss نیز می‌تواند Model باشد و الزاماً پارامتر آموزش‌پذیر ندارد. تعریف ورودی/خروجی معرفی Quantity است، نه مقادیر زمان اجرا.
- مدل ممکن است محورهایی را تجمیع کند و محورهای خروجی با ورودی برابر نباشند. قرارداد دقیق attribute تجمیع هنوز در حال بررسی است.
- geometry مدل باید با دامنهٔ Fieldهای ورودی و خروجی سازگار بررسی شود. مثلاً normal سطحی روی مرز تعریف می‌شود و مصرف‌کنندهٔ آن باید روی دامنهٔ مرزیِ مربوط معتبر باشد؛ صرف داشتن ورودی برداری به معنی normal نیست. مدل می‌تواند به دامنه‌ای محدودتر از دامنهٔ بعضی Fieldها محدود شود؛ قواعد دقیق این بررسی بعداً همراه geometry تعیین شوند. خروجی غیرمکانی پس از تجمیع الزاماً geometry ندارد، ولی مدل انتگرال‌گیری همچنان دامنهٔ مکانی مصرف Field را می‌شناسد.
- قرارداد init فعلاً شامل inputs: List[Quantity]، outputs: List[Quantity] و geometry است. کاربر اصل این قرارداد را پذیرفته است؛ اختیاری‌شدن geometry در پیشنهاد جدید زیر بررسی می‌شود.
- geometry مدل فعلاً هنگام init مشخص می‌شود؛ اتصال مدل‌های دارای geometry متفاوت باید خطا بدهد. (این قرارداد قابل بازبینی است.) اتصال هنگام init به معنی ثابت‌بودن شکل یا پارامترهای geometry نیست. معیار دقیق تشخیص geometry یکسان هنوز باید انتخاب شود؛ صرف یکسان‌بودن کلاس کافی نیست.
- جهت پیشنهادی برای config ترکیب مدل‌ها: تعریف رابطه به صورت متن ریاضی و استفاده از SymPy برای نمایش و تحلیل عبارت. نحوهٔ ساخت مدل اجرایی، مجموعهٔ عملگرها و بررسی شکل خروجی‌ها هنوز باز است؛ SymPy به‌تنهایی هماهنگ‌کنندهٔ مدل‌های آموزش‌پذیر محسوب نمی‌شود.

## تصمیم‌های صریحاً موکول‌شده

### پیشنهاد جاری: تفکیک Quantity و Field

کاربر پیشنهاد کرده است geometry دامنهٔ کمیت فقط برای fieldهای مکانی مشخص شود و Field زیرکلاس Quantity باشد. پیشنهاد پاسخ: Quantity برای داده/پارامتر عمومی، Field برای مقدار تعریف‌شده در نقاط یک دامنه با geometry مشخص. point cloud ورودی encoder، مجموعهٔ نقاط است و صرف داشتن مختصات آن را field نمونه‌برداری‌شونده در نقاط درخواست تبدیل نمی‌کند.

برای Model پیشنهاد جدید، geometry: Geometry | None = None است: مدل محاسبهٔ جرم از شعاع و چگالی و encoder عمومی هندسه لازم نیست دامنهٔ مکانی ثابتی داشته باشند. geometry مدل بیانگر دامنهٔ اجرای مکانی آن باشد، نه هر هندسه‌ای که داده‌های ورودی به آن مربوط‌اند. پذیرش نهایی این تفکیک و امضای اصلاح‌شده هنوز باز است. اثر این تغییر بر هویت Quantityهای بدون geometry و قواعد اتصال را بعداً بررسی کنیم؛ بحث مرز و اشتراک فعلاً باز نشود.

### ۱. نمایش مقدار یک Quantity

آیا مقدار، tensor ساده است یا شیئی شامل tensor و اطلاعاتی مانند نسخه، نقاط و محدودهٔ اعتبار؟ این موضوع عمداً برای بعد گذاشته شده است.

پیشنهاد تازهٔ کاربر: برای T(x, y, pc)، مقدار T همراه ارجاع به ورودی‌های x، y و pc معرفی شود تا وابستگی‌ها بدون کپی داده‌ها مشخص باشند. این پیشنهاد هنوز پذیرفته یا رد نشده است. تعریف نمادین وابستگی، نگهداری ورودی‌های یک ارزیابی و تشخیص اعتبار نتیجه سه موضوع متفاوت‌اند؛ به‌ویژه وزن مدل نیز روی نتیجه اثر دارد. تکرار نمایشی pc برای هر نقطه، سیاست broadcasting/grouping و جزئیات حافظه برای بعد می‌مانند.

### ۲. ارتباط Model و Geometry

تصمیم موقت جدید: geometry هنگام init مشخص شود و اتصال مدل‌های روی geometry متفاوت خطا بدهد. این موضوع دیگر کاملاً موکول‌شده نیست؛ بازبینی قرارداد در آینده و تعریف معیار یکسان‌بودن geometry همچنان باز است.

بحث جدید، هنوز قطعی‌نشده: متفاوت‌بودن شیء geometry الزاماً به معنی ناسازگاری دامنه نیست. اگر دامنهٔ یک مدل boundary هندسهٔ G و دامنهٔ مدل دیگر G باشد و مدل دوم روی مرز نیز معتبر باشد، ترکیب نقطه‌ای می‌تواند روی boundary انجام شود. رابطهٔ زیرمجموعه/والد باید قابل اعتماد و صریح باشد؛ قاعدهٔ اولیهٔ خطا برای geometry متفاوت در پرتو این موضوع در حال بازبینی است. دامنهٔ قابل ارزیابی مدل با هندسه‌ای که برای encoder استفاده می‌شود یکی فرض نشود.

به درخواست کاربر، بررسی قراردادهای مرز، اشتراک و زیرمجموعهٔ geometry فعلاً متوقف شود. اول قرارداد Model، fieldها و methodهای آن روشن شود؛ سپس با توجه به کار همکاران روی geometry و geometry encoder، قرارداد آن بخش بررسی شود. تا آن زمان geometry در قرارداد مدل فقط مرجعِ تعیین‌شده هنگام init است و این یادداشت API هندسی جدیدی تحمیل نمی‌کند.

یک geometry می‌تواند شکل و پارامترهای متغیر داشته باشد و همچنان از همان کلاس باشد. باید اتصال مدل به دامنه را از استفادهٔ محاسباتی مدل از پارامترها یا point cloud هندسه جدا بررسی کنیم. مدل‌های چندمحیطی و encoder هندسه باید قابل بیان باشند.

### ۳. شکل کلی ارتباط اجزا

ساختار الزاماً زنجیرهٔ ساده نیست؛ کاربر خواسته است دربارهٔ چند مسیر و ارتباط آن‌ها بیشتر فکر کند. هنوز ساختار نهایی انتخاب نشده است.

## پیشنهادها و پرسش‌های تکمیلیِ هنوز قطعی‌نشده

### ۴. نام و مسئولیت جزء محاسباتی

Model برای نگاشت ورودی به خروجی، Network برای شبکهٔ عصبی داخلی و Solver برای حل عددی پیشنهاد شده‌اند؛ نام‌گذاری نهایی هنوز قطعی نشده است. باید مرز مدل، محاسبهٔ مشتق و فرایند حل مشخص شود.

### ۵. خروجی‌های درخواست‌شده

پیشنهاد: مصرف‌کننده علاوه بر ورودی‌ها، کمیت‌های خروجی موردنیازش را اعلام کند. جزئیات API و نحوهٔ تجمیع درخواست چند مصرف‌کننده هنوز باز است.

انتخاب termهای فعال می‌تواند داخل مدل loss یا بیرون آن انجام شود؛ کاربر خواسته است فعلاً دربارهٔ محل این مسئولیت تصمیم نگیریم. تفکیک پیشنهادی قبلیِ این مسئولیت از Model قطعی نیست.

### پیشنهاد ردشده: فهرست روش‌های تجمیع

پیشنهاد اولیهٔ reductions شامل فهرست mean/sum/max توسط کاربر رد شد: Model کلاس انتزاعی مانند nn.Module است، نه یک مدل عمومی با الگوریتم تجمیع ازپیش‌تعیین‌شده. قرارداد مدل رفتار محورها را معرفی می‌کند؛ الگوریتم، یادگرفتنی یا دستی، در پیاده‌سازی آن آزاد است. این فهرست دیگر پیشنهاد جاری نیست.

انتگرال همچنان به وزن‌های متناسب با دامنه/روش نمونه‌برداری نیاز دارد؛ تعیین محاسبه در اختیار پیاده‌سازی مدل است. کاهش‌های تعبیه‌شده داخل encoder/شبکه نباید دوباره توسط مسیر عمومی اعمال شوند.

### پیشنهاد جاری: قرارداد تابعِ یک نمونه و محورهای پردازش داخلی

کاربر پیشنهاد کرده است کتابخانه تابع مدل برای یک سناریو/نقطه را با vmap یا روش مشابه batch کند. پیشنهاد پاسخ: این پیش‌فرض برای مدل‌های نقطه‌ای مناسب است، ولی عمومی و اجباری نباشد. مدل باید مشخص کند کدام محورها در هر فراخوانی کامل به تابع داده شوند و کدام محورها مستقل‌اند و کتابخانه می‌تواند روی آن‌ها map کند. خروجی‌ها نیز محورهای باقی‌مانده را معرفی کنند؛ نام روش reduction لازم نیست.

دریافت کل محور نقاط الزاماً به معنی reduction نیست؛ attention یا operator می‌تواند تمام نقاط را بخواند و خروجی نقطه‌ای بدهد. خروجی اسکالر ممکن است محور نقاط را حذف کند. همان امضای ورودی/خروجی برای شکل و اتصال خروجی‌ها کاربرد دارد و attribute جداگانهٔ روش reduction فعلاً لازم نیست. vmap وعدهٔ حذف محاسبات تکراری branch/encoder نمی‌دهد؛ اشتراک آن‌ها با ترکیب صریح مدل‌ها بررسی شود. این قرارداد و نحوهٔ پیاده‌سازی batching هنوز پیشنهاد هستند.

### نتیجهٔ بررسی ابزارهای امضا و batching — ۲۰۲۶-۱۰-۱۳

کاربر امکان عملیِ پیاده‌سازی batching از روی امضا را پذیرفته است. انتخاب کتابخانه و API دقیق Model هنوز نهایی نیست؛ این پذیرش به معنی سازگاری هر پیاده‌سازی دلخواه با vmap یا حذف خودکار محاسبات تکراری نیست.

- [einx.torch.adapt_with_vmap](https://einx.readthedocs.io/en/latest/api/adapters/torch/einx.torch.adapt_with_vmap.html) تابع کاربر را می‌گیرد و از متن محورهای ورودی/خروجی، vmapهای لازم را می‌سازد؛ معادل JAX هم دارد. محورهای داخل براکت کامل به تابع داده می‌شوند و محورهای بیرون براکت با map مدیریت می‌شوند. [نمونهٔ رسمی کد تولیدشده](https://github.com/fferflo/einx#which-operations-are-supported) ساخت vmapهای تو‌در‌تو را نشان می‌دهد. این adapter تابع است؛ نگهداری امضا روی Model و اتصال آن به mapping کمیت‌ها همچنان مسئولیت قرارداد ماست.
- مثال تابع دو اسکالر به یک اسکالر: `s, s p -> s p` برای نقاط مخصوص هر سناریو؛ `s, p -> s p` برای نقاط مشترک؛ `s, s -> s` برای جفت‌های متناظر. مثال تابعی که تمام نقاط را یکجا مصرف می‌کند و یک اسکالر می‌دهد: `s, s [p] -> s`. در مثال آخر الگوریتم داخلی تابع آزاد است، نه محدود به mean/sum/max.
- [jax.numpy.vectorize](https://docs.jax.dev/en/latest/_autosummary/jax.numpy.vectorize.html) امضای core مانند `(),()->()` می‌گیرد و با vmap و broadcasting محورهای اضافه را مدیریت می‌کند. برای دمای سناریو با شکل `(S,)` و مکان‌های `(S,P)` باید ورودی دما هنگام فراخوانی به `(S,1)` تبدیل شود. برخلاف einx، این امضا به‌تنهایی نام و تعلق محورهای batch را بیان نمی‌کند.
- [Haliax](https://haliax.readthedocs.io/en/latest/vmap/) گزینهٔ مرتبط برای محورهای نام‌دار است. [Flax vmap](https://flax-linen.readthedocs.io/en/latest/api_reference/flax.linen/transformations.html) خود Module و وضعیت/پارامترهای آن را مدیریت می‌کند، ولی تنظیم محورهای map را می‌خواهد. [NumPy vectorize](https://numpy.org/doc/stable/reference/generated/numpy.vectorize) امضا می‌گیرد اما پیاده‌سازی اساساً حلقه است؛ شاهد اجرای سریع با vmap نیست.

این نتایج از بررسی مستندات و مخزن ابزارها ثبت شده‌اند؛ einx در محیط فعلی نصب نیست و مثال آن در این پروژه اجرا نشده است. پیش از انتخاب وابستگی، یک آزمایش محدود برای مدل نقطه‌ای، مصرف کل نقاط و مشتق‌گیری لازم است.

### بحث جاری: اندازه‌ها در حالت یک نقطه برای هر سناریو

کاربر حالت سه سناریو و دو نقطه برای هر سناریو را پذیرفته است: دو کمیت با شکل ذاتی `()`؛ دمای مرز `(3,)`، مکان `(3,2)` و خروجی دما `(3,2)`. محورهای batch جزو شکل ذاتی Quantity نیستند. دمای مرزِ غیرمکانی برای هر سناریو یک مقدار دارد و به محور نقطه نیاز ندارد.

برای `points_per_scenario=1` تصمیم هنوز باز است: مکان و خروجی می‌توانند به صورت `(S,)` با محور جفت سناریو-نقطه یا `(S,1)` با دو محور جدا معرفی شوند. پیشنهاد پاسخ، حفظ `(S,1)` است تا تغییر تعداد نقاط از یک به دو فقط اندازهٔ محور نقطه را تغییر دهد، نه تعداد و معنای محورها. این شکل به معنی دو برابرشدن حافظه نیست؛ تعداد عناصر همان S است. کتابخانه می‌تواند هنگام اجرای تابع نقطه‌ای محورهای batch را مدیریت کند؛ تابع کاربر همچنان اسکالر می‌گیرد. flatten احتمالی برای اجرای داخلی، از قرارداد عمومی جداست و هنوز تصمیم اجرایی ندارد.

این پیشنهاد هنوز تأیید نهایی کاربر را ندارد. فعلاً فقط همین انتخاب محورهای حالت یک نقطه بررسی شود؛ نمایش حافظه، cache و قواعد geometry باز نشوند.

### ۶. نسخه، تغییر و اعتبار نتیجه

پیشنهاد: پاسخ هر خروجی نسخهٔ جدا داشته باشد. استفادهٔ مجدد بر اساس درخواست، نسخهٔ ورودی‌های مستقیم و وضعیت داخلی مؤثر مثل وزن مدل باشد. هنوز قرارداد دقیق نسخه و اعتبار نتیجه، به‌ویژه مسیر مشتق‌گیری در آموزش، انتخاب نشده است.

### ۷. نگهداری خروجی‌ها و محاسبات میانی

کاربر نگهداری خروجی‌های لایه را مطرح کرده است؛ پیشنهاد جایگزین، تفکیک نگهداری اطلاعات نسخه از نگهداری خود مقدار است. محاسبات میانی لازم برای مشتق‌گیری باید تا زمان مصرف باقی بمانند. سیاست حافظه، زمان آزادسازی و امکان استفادهٔ مجدد هنوز قطعی نیست.

ارجاع مستقیم به tensorهای ورودی می‌تواند عمر حافظهٔ آن‌ها را طولانی کند. ایدهٔ نگه‌داشتن هویت شیء پس از آزادسازی داده، و انتخاب بین نگهداری/بازمحاسبهٔ محاسبات میانی، فعلاً موضوع طراحی آینده است؛ نباید قرارداد اولیهٔ Model را بر اساس دستکاری storage یک Tensor بنا کنیم.

### ۸. مدل ترکیبی و چندمحیطی

تصمیم موقت ثبت‌شده در پایهٔ توافق: ترکیب سری/شاخه‌ای روی یک دامنه می‌تواند Model باشد؛ هماهنگی مدل‌های محیط‌های متفاوت فعلاً Model محسوب نمی‌شود. نام و قرارداد جزء هماهنگ‌کنندهٔ چندمحیطی هنوز باز است. شرط اتصال فیزیکی محیط‌ها نیز باید از صرفِ کنار هم گذاشتن پیش‌بینی‌ها تفکیک شود.

### ۹. موازی‌سازی و دسته‌ای‌کردن اجرا

آیا هماهنگی مسیرهای مستقل داخل مدل ترکیبی است یا جزء دیگری؟ تحویل پاسخ با هم الزاماً به معنی اجرای همزمان نیست. استقلال مسیرها، اشتراک محاسبات، اجرای دسته‌ای شبکه‌های مشابه و محدودیت حافظه/سخت‌افزار باید جدا بررسی شوند؛ اجرای موازی هنوز تصمیم قطعی نیست.

### ۱۰. ارتباط نمونه‌برداری با مدل و قوانین

پیشنهاد: نقاط نمونه‌برداری متعلق به نیاز یک قانون/درخواست باشند؛ یک مدل ممکن است روی نقاط داخلی، مرزی، داده و اتصال استفاده شود. مالکیت sampler و سیاست اشتراک نمونه در هر مرحله هنوز قطعی نیست.

### ۱۱. نمایش نمادین کمیت‌ها

نمایش آینده در SymPy مطرح شده است. باید مشخص شود هویت کمیت، شکل، واحد و وابستگی نمادین به مختصات چگونه بیان می‌شوند؛ مثلاً T(x, y) با نماد سادهٔ T فرق دارد. ساختار نهایی Quantity هنوز انتخاب نشده است.

## تمرکز قدم بعد

تمرکز فعلی، قرارداد محورهایی است که تابع مدل در هر فراخوانی دریافت/تولید می‌کند و امکان batchکردن بیرونی آن؛ پیشنهاد فهرست روش‌های تجمیع رد شده است. نمایش حافظهٔ Value، مکان مسئولیت termهای فعال و قواعد روابط هندسی فعلاً برای بعد باز بمانند.

بحث جدید به قابلیت‌های sampler و ترجیح سادگی بر انعطاف عمومی رسیده است. [پیشنهاد حداقلی sampler با شواهد مقاله](sampler_minimal_proposal.fa.md) دو layout مشترک و نقاط جدا برای هر سناریو با تعداد برابر را پیشنهاد می‌کند؛ این هنوز تصمیم نهایی نیست. تعدادهای متغیر، نگاشت زیرمجموعهٔ دلخواه و بهینه‌سازی هم‌پوشانی جزئی برای بعد پیشنهاد شده‌اند. نیاز احتمالی point cloud encoder به تعداد متفاوت نقاط، از تعداد نقاط residual جداست.

بحث جاری به قرارداد batch ورودی/خروجی Model رسیده است. [پیشنهاد حالت‌ها و قرارداد batch](model_batch_contract_proposal.fa.md) برای بررسی نوشته شده و هنوز پذیرفته‌شده نیست. انتخاب نام Field، تعلق داده‌ها به نمونه‌ها و مجموعه‌نقاط، و تفاوت Quantity غیرمکانی با Field محور بحث‌اند؛ قرار نیست تصمیم‌های cache و حافظه همزمان پیش بروند.

به درخواست کاربر، بحث‌ها یکی‌یکی پیش بروند. قدم فعلی، مشخص‌کردن قرارداد Model و fieldها و methodهای آن است؛ بحث روابط هندسی به بعد از این مرحله منتقل شد. معرفی ورودی/خروجی و اتصال branch، trunk و عمل ترکیب در مثال DeepONet مبنا باقی می‌مانند. نمایش حافظهٔ مقادیر، cache/نسخه، آزادسازی محاسبات میانی، broadcasting و هماهنگی multi-medium فعلاً باز بمانند. اسکلت Model تا توافق بعدی پیشنهاد است، نه API اجرایی نهایی.

## اسکلت کلاس‌ها — ۲۰۲۶-۱۰-۱۶

به درخواست کاربر، اسکلت قراردادهای بحث‌شده در pinnlab/contracts.py (legacy PINNlab: `pinnlab/contracts.py`) نوشته شد. این فایل از Solver و Sampler اجرایی فعلی مستقل است و به exportهای اصلی pinnlab اضافه نشده است.

- Quantity و زیرکلاس Field، با شکل ذاتی جدا از محورهای نمونه، هویت بر اساس نام و همان شیء geometry، و تشخیص شکل‌های متناقض در تعریف‌های هم‌زمان زنده.
- Axis برای نام محور، مستقل از اندازه و موقعیت آن در tensor. استفاده از نام یکسان به معنی محور یکسان در این نمایش اولیه است؛ دو محور مستقل نام متفاوت می‌خواهند.
- Signature برای محورهایی که یک فراخوانی تابع کامل مصرف/تولید می‌کند؛ هر Quantity نگاشت جدا دارد و shape ذاتی آن دوباره در این امضا نوشته نمی‌شود.
- Model انتزاعی با inputs، outputs، geometry اختیاری، signature و evaluate. مقدار با یک پارامتر نوع عمومی معرفی شده و هنوز Tensor یا wrapper خاصی نیست.
- CompositeModel انتزاعی برای ترکیب سری/شاخه‌ای روی یک دامنه؛ معرفی اعضا دارد ولی parser، ترتیب اجرا و graph اجرایی ندارد.

این نمایش ساختاری Signature و نام evaluate انتخاب‌های قابل بازبینیِ اسکلت هستند. قرارداد تابع کاربر از layout دادهٔ زمان اجرا جداست؛ تولید خودکار vmap، تطبیق محورها و اطلاعات تعلق نمونه‌ها هنوز پیاده‌سازی نشده‌اند. به‌ویژه نام محور سناریو ممکن است به بیش از یک محور واقعی مربوط شود و نباید به شمارهٔ ثابت محور در tensor وابسته شویم؛ قرارداد این حالت هنوز باید دقیق شود.

Field و اختیاری‌بودن geometry برای مدل‌های غیرمکانی، مطابق جمع‌بندی اخیر گفت‌وگو وارد اسکلت شدند. بررسی روابط geometry، نمایش Value، cache، نسخه و سیاست حافظه همچنان بازند. انتخاب library برای batching قطعی نیست؛ امضای JAX به‌تنهایی معنای محورهای زمان اجرا را نمی‌دهد.

Sampler بودنِ sampler سناریو، رابطهٔ PointSampler و ScenarioSampler، زیرکلاس Model بودن یا نبودن Sampler و روش merge هنوز توافق نهایی ندارند؛ برایشان API جدید نوشته نشده است. حالت‌های points_per_scenario، جفت‌کردن هر نقطه با سناریو، سناریوهای چندگانه برای هر نقطه و نقاط مشترک باید در بحث بعدی بررسی شوند. پیشنهاد قبلیِ اجباری‌کردن فقط دو محور در همهٔ حالت‌ها نهایی نشده است.

## اصلاح قراردادها به درخواست کاربر — ۲۰۲۶-۱۰-۱۷

این بخش، توصیف اسکلت فعلی را جایگزین بخش تاریخیِ ۲۰۲۶-۱۰-۱۶ می‌کند:

- Quantity دوباره با constructor عادی ساخته می‌شود؛ شیءهای مستقل با نام و همان geometry برابرند و hash یکسان دارند. روش Quantity.get انتخاب نشده است. کلاس داخلی _QuantityDefinition و نگهداری سراسری تعریف‌ها حذف شدند؛ وجود آن‌ها برای برابری Quantity لازم نبود.
- شکل جزو هویت نیست؛ سازگاری شکل تعریف‌های هم‌هویت هنگام معرفی آن‌ها در یک Signature بررسی می‌شود، نه در constructor با تکیه بر وضعیت سراسری. dictionary پایتون ممکن است کلیدهای برابر را پیش از تحویل به Signature ادغام کند؛ این بررسی نمی‌تواند تعریف حذف‌شده را بازیابی کند. بررسی اتصال امضای مدل‌های مختلف همچنان کار موتور ترکیب آینده است.
- Geometry در فایل قراردادهای جدید یک ABC مستقل با boundary، union، intersection، difference و is_subset_of است؛ is_superset_of و عملگرهای |، & و - به همین متدها واگذار می‌شوند. تشخیص زیرمجموعه‌ای که معلوم نیست باید خطا بدهد، نه False. الگوریتم هندسی و اتصال آن به Geometry اجرایی فعلی هنوز پیاده‌سازی نشده است.
- Signature برای محورها Axis یا string می‌پذیرد و آن‌ها را به tuple از Axis تبدیل می‌کند. یک string تنها، نام یک محور است؛ برای چند محور sequence می‌دهیم. from_string اضافه شده و طبق درخواست فعلاً فقط NotImplementedError می‌دهد؛ دستور زبان متن هنوز انتخاب نشده است.
- Model دیگر constructor اجباری برای این مشخصات ندارد: signature و geometry property انتزاعی‌اند که زیرکلاس باید ارائه کند؛ class attribute مشخص نیز می‌تواند این قرارداد را برآورده کند. inputs و outputs از signature استخراج می‌شوند تا معرفی تکراری لازم نباشد. زیرکلاس می‌تواند constructor دلخواه داشته باشد و مشخصات را آنجا ذخیره کند؛ آنچه اجباری است در دسترس بودن قرارداد است، نه روش مقداردهی آن.

- در اصلاح بعدی همین روز، به درخواست کاربر Generic و ValueT حذف شدند. فعلاً `Value = torch.Tensor` است و Model و CompositeModel پارامتر نوع ندارند؛ نوع مقدار در یک alias متمرکز است تا بعداً قابل بازبینی باشد.

کامنت‌ها و docstringهای کد انگلیسی باقی ماندند. قرارداد Sampler، اجرای batching، حافظه و cache تغییر نکردند و هنوز بازند.

## Value و batching در خود مدل — ۲۰۲۶-۱۰-۱۸

با تأیید کاربر، Value دیگر alias برای Tensor نیست؛ dataclass با دو عضو tensor و axes است. axes نام محورهای نمونهٔ واقعی داده را نگه می‌دارد و stringها به Axis تبدیل می‌شوند. شکل ذاتی Quantity همچنان جداست. Tensor با ارجاع نگهداری می‌شود؛ کپی یا detach نمی‌شود. خود اعضای Value ثابت‌اند، ولی این به معنی تغییرناپذیری محتوای Tensor نیست.

- evaluate ورودی و خروجی dict از Quantity به Tensor خام دارد و فقط امضای محاسباتی یک فراخوانی را می‌بیند.
- evaluate_batched روی Model پیاده‌سازی شد: dict از Quantity به Value می‌گیرد، محورهای core را طبق Signature مرتب می‌کند، روی محورهای اضافی vmap می‌سازد و نتیجه را همراه محورهای خروجی در Value قرار می‌دهد. Modelهای غیر nn.Module نیز این متد را دارند.
- forward در TorchModel همان evaluate_batched را صدا می‌زند؛ __call__ خود nn.Module دست‌نخورده است و hookها و پارامترها مسیر معمول PyTorch را دارند.
- ModelConnector اکنون Valueها را بین مدل‌ها جابه‌جا می‌کند. آرگومان جداگانهٔ axes و متد output_axes حذف شدند، چون هر خروجی محورهای خودش را همراه دارد. منطق vmap از اتصال‌دهنده به Model منتقل شد و تکرار نشده است.

قرارداد قبلیِ Value = torch.Tensor با این تصمیم جایگزین شد. نسخه، cache و وابستگی‌ها هنوز اضافه نشده‌اند؛ توسعهٔ بعدی این dataclass ممکن است ولی قراردادشان نهایی نیست. Solver با خروجی‌های انتخابی، نمایش گراف و بررسی compile قدم‌های بعدند و در این تغییر پیاده‌سازی نشده‌اند.

## تجمیع فایل‌ها، محور متنی و Solver — ۲۰۲۶-۱۰-۱۸

به درخواست کاربر همهٔ کدهای آزمایشی به contracts.py منتقل شدند و model_composition.py حذف شد. کلاس Axis حذف و `Axis = str` شد؛ axes در Value و Signature به tuple از نام‌های متنی تبدیل می‌شوند.

- TorchModel و ModelConnector اکنون در همان فایل‌اند. Solver از TorchModel و CompositeModel ارث می‌برد؛ هم Model است و هم nn.Module و پارامترهای اعضا ثبت می‌شوند.
- در ساخت Solver، outputs خروجی یا خروجی‌های ثابت forward را مشخص می‌کند. یک خروجی به شکل Tensor و چند خروجی به شکل tuple با ترتیب تعیین‌شده برمی‌گردند.
- evaluate طبق قرارداد Model ورودی/خروجی Tensor خام دارد و همهٔ خروجی‌های تولیدشده، از جمله نتایج میانی، را برمی‌گرداند. evaluate_batched آن‌ها را با Value و محورهایشان می‌دهد. forward از همان مسیر استفاده می‌کند و فقط خروجی‌های انتخابی را بیرون می‌دهد.
- مطابق تصمیم شروع ساده، مدل‌های نامرتبط هنوز دستی حذف نمی‌شوند و موازی‌سازی دستی نداریم. کد به compile وعدهٔ حذف تمام کار اضافه نمی‌دهد؛ نتیجهٔ بهینه‌سازی باید اندازه‌گیری شود.
- input_axes در constructor Solver امضای محورهای کاملِ evaluate خودش را مشخص می‌کند، نه layout یک batch زمان اجرا. مثلاً `{x: "point"}` یعنی تابع Solver همهٔ نقاط را یکجا می‌بیند؛ سناریوی اضافی روی Value بیرونی با vmap مدیریت می‌شود. وقتی مسیر داخلی محور کامل می‌خواهد و این اطلاعات از مرز Solver قابل تعیین نیست، باید input_axes داده شود. امضای خروجی‌ها از این قرارداد و امضای اعضا استخراج می‌شود؛ حدس‌زدن تعلق محورها از روی اندازه انجام نمی‌شود.
- to_mermaid نمایش گراف را از همان وابستگی‌های اجرایی تولید می‌کند؛ مدل‌ها گره و Quantityها برچسب یال‌اند. Solver می‌تواند عضو یک اتصال‌دهندهٔ دیگر هم باشد؛ آن مسیر از evaluate_batched استفاده می‌کند چون forward ممکن است فقط Tensor منتخب بدهد.
- MappingProxyType از Signature برداشته شد؛ دیکشنری‌های ورودی همچنان کپی می‌شوند، ولی mappingproxy با کلید Quantity در torch.compile پشتیبانی نشد. فیلدهای dataclass ثابت‌اند؛ قراردادهای مدل هنگام استفاده تغییر نکنند.

بررسی compile با fullgraph=True و backendهای eager و aot_eager، همراه backward، موفق بود. backend پیش‌فرض Inductor به دلیل نبود کامپایلر C++ با نام cl در محیط اجرا نشد؛ بنابراین سرعت یا کد تولیدشدهٔ آن تأیید نشده است. Solver جدید از pinnlab.contracts وارد می‌شود و Solver کتابخانهٔ قبلی در namespace اصلی تغییر نکرده است.

## ساده‌سازی Model و Solver — ۲۰۲۶-۱۰-۱۸

این تصمیم جایگزین شرح Solver در بخش قبلی است:

- Model مستقیماً از nn.Module و ABC ارث می‌برد. evaluate همچنان محاسبهٔ اصلی با Tensor خام است؛ forward جای evaluate_batched را گرفته و دیکشنری Quantity به Value را با vmap خودکار پردازش می‌کند. فراخوانی معمول model(values) است تا hookهای PyTorch اجرا شوند. constructor زیرکلاس باید super().__init__() را صدا بزند.
- TorchModel و ModelConnector حذف شدند. منطق مرتب‌سازی وابستگی‌ها، اتصال خروجی‌ها به ورودی‌ها، ثبت پارامترهای اعضا، بررسی‌های سازگاری و نمایش گراف همگی در Solver قرار دارند.
- Solver فقط از nn.Module ارث می‌برد و Model یا CompositeModel نیست. evaluate، signature و input_axes ندارد؛ هر عضو خودش محورهای Value را مطابق Signature خود مدیریت می‌کند. Solver در این نسخه به‌عنوان عضو Solver دیگر پذیرفته نمی‌شود.
- Solver.forward نیز دیکشنری Quantity به Value برمی‌گرداند؛ برای گرفتن loss از result[loss].tensor استفاده می‌کنیم. outputs خروجی‌های انتخابی و ترتیب دیکشنری را مشخص می‌کند؛ اگر داده نشود همهٔ خروجی‌های تولیدشده برمی‌گردند.
- همهٔ مدل‌های عضو همچنان اجرا می‌شوند؛ انتخاب خروجی به معنی حذف شاخه‌های نامرتبط نیست. نتیجهٔ مشترک در همان فراخوانی دوباره استفاده می‌شود. سیاست geometry فعلاً همان یکسان‌بودن آبجکت geometry غیرتهی اعضاست؛ روابط زیرمجموعه همچنان تصمیم باز هستند.

به درخواست بعدی کاربر، CompositeModel نیز حذف شد؛ در قرارداد فعلی Model برای محاسبه و Solver برای اتصال مدل‌ها باقی می‌مانند.

## محور geometry به شکل لیست و زمان بررسی سازگاری — ۲۰۲۶-۱۰-۲۴

تصمیم طراحی برای ادامهٔ کار؛ پشتیبانی از این نمایش و بررسی‌های زیر هنوز پیاده‌سازی نشده‌اند:

- در روش اول، محور بیرونی geometry با لیست Tensorها نمایش داده می‌شود تا تعداد رأس‌ها، نقاط یا اتصال‌ها بین geometryها متفاوت باشد. روش‌های دیگر نمایش batch فعلاً موضوع این تصمیم نیستند.
- اگر evaluate محور geometry را کامل نخواهد، موتور فعلاً اعضای لیست را با حلقه پردازش می‌کند. اگر آن محور را کامل بخواهد، لیست به تابع داده می‌شود؛ محورهای اضافیِ مشترک در Tensorهای داخل لیست همچنان می‌توانند با vmap پردازش شوند، مشروط به سازگاری عملیات تابع.
- هر محور مشترکی که هم‌زمان پیمایش می‌شود باید در اعضای مربوط طول برابر داشته باشد. مثلاً دریافت کامل geometry ولی دریافت‌نکردن point برای دو geometry با ۲۰ و ۴۰ نقطه، در قرارداد فعلی نامعتبر است و باید پیش از فراخوانی evaluate خطا بدهد. نه حاصل‌ضرب نقاط، نه برش و نه تطابق دلخواه را خودکار فرض نمی‌کنیم. اگر تابع هر دو محور را کامل بگیرد، تفاوت تعداد نقاط به‌خودی‌خود مانع نیست.
- نام محور مشترک، اعلام تطابق نمونه‌هاست؛ برابر بودن اندازه به‌تنهایی تطابق معنایی را اثبات نمی‌کند. ورودی فاقد یک محور پیمایش‌شده می‌تواند در امتداد آن مشترک باشد.
- فعلاً بررسی سازگاری بر اساس Signature و دادهٔ واقعی، هنگام اجرا و درست پیش از محاسبه انجام شود؛ منظور از just in time در این تصمیم، اعتبارسنجی زمان اجراست، نه JIT compilation.

**کار ضروری برای بعد:** راهی طراحی کنیم که ناسازگاریِ محورهای کامل و محورهای پیمایش‌شده، تا حد امکان همان هنگام تعریف/ساخت Solver تشخیص داده شود. برای این کار باید مشخص شود چه اطلاعاتی دربارهٔ ساختار لیستی، وابستگی محورها و اندازه‌ها در قراردادها اعلام می‌شود. سازوکار هنوز انتخاب نشده است؛ اطلاعات وابسته به داده که هنگام ساخت معلوم نیستند همچنان به بررسی زمان اجرا نیاز خواهند داشت.

از main، Geometry و Field و وابستگی‌های domain حذف شدند؛ Model دیگر geometry لازم ندارد،
Solver و ComputationGraph تطابق geometry بررسی نمی‌کنند و هویت Quantity فعلاً فقط نام است.
این تصمیم، قراردادهای هندسی توضیح‌داده‌شده در بخش‌های تاریخی این یادداشت را فعلاً کنار می‌گذارد.
لیست Tensorها، محورهای نام‌دار و نیاز اضافهٔ backend به mesh مستقل از این قرارداد باقی‌اند.

ایده‌های زیر طرح‌های توسعهٔ نسبتاً مشخص برای پیاده‌سازی بعدی‌اند؛ جزئیات و نمونهٔ اجرایی
مرتبط در بخش مستقلِ [multi-domain و partial AD](#multi-domain-geometry-and-partial-ad) ثبت شده‌اند.
این‌ها تصمیم‌های معوق محسوب نمی‌شوند و در عین حال API فعلی main نیستند:

- GeoCore بتواند چند geometry را مدیریت کند.
- نمونه‌برداری و دریافت mesh و representation هر geometry به‌صورت مستقل انجام شود.
- کمیت‌های میدان بتوانند attribute به نام domain داشته باشند که به geometry تعریفشان اشاره کند.

نحوهٔ اتصال GeoCore به موتور، هویت domain، رابطهٔ چند domain و شکل دقیق کمیت میدان بعداً
طراحی می‌شوند؛ فعلاً API یا subclass جایگزین برای آن‌ها اضافه نمی‌کنیم.

اعتبارسنجی این حذف: هر ۷۴ تست و اجرای کامل نوت‌بوک دما، شامل آموزش و backward از residual
فیزیکی، موفق بودند. یک تست صریح نبود Geometry/Field در API عمومی را نیز بررسی می‌کند.

مرجع اجرایی محفوظ: branch `partial-derivative-and-geometry-domain-support`، commit `12d97a1`.

### ۱. GeoCore و چند domain مستقل

GeoCore بتواند چند geometry را مدیریت کند و نمونه‌برداری، mesh و representation هر geometry
مستقل قابل دریافت باشد. برای مثال solid و liquid دو domain مجزا هستند؛ یک representation
مشترک یا یک sampler واحد نباید پیش‌نیاز استفاده از آن‌ها باشد. پارامترهای هندسه نیز می‌توانند
از نمونه‌برداری بالادستی بیایند و تولید representation به آن‌ها وابسته باشد.

کمیت‌های میدان بتوانند `domain` داشته باشند که به geometry تعریفشان اشاره کند. دو میدان
هم‌نام روی دو domain متفاوت، مثل دمای جامد و دمای سیال، کمیت یکسانی نیستند. کمیت‌های غیرمکانی،
مانند چگالی یک نمونه یا embedding خروجی encoder، لزوماً domain نمی‌خواهند. اشاره به geometry
برای معرفی دامنه است؛ Tensor، mesh فعلی یا نسخهٔ نتیجه نباید داخل تعریف Quantity ذخیره شود.

کار روی مرز، زیرمجموعهٔ یک domain و سطح مشترک دو محیط نیز در همین جهت توسعه قرار می‌گیرد.
مثلاً یک مدل روی کل جامد و مدلی روی مرز آن می‌توانند روی دامنهٔ معتبر مشترک ترکیب شوند.
این یک ایدهٔ توسعه است؛ تشخیص خودکار سطح مشترک جامد/سیال یا سازگاری domainها در branch
محفوظ پیاده نشده است.

### ۲. قرارداد هندسی‌ای که در branch اجرا شده بود

- `Geometry` قرارداد انتزاعی boundary، union، intersection، difference و is_subset_of داشت؛
  is_superset_of از رابطهٔ معکوس استفاده می‌کرد و عملگرهای |، & و - میان‌بُر بودند.
  الگوریتم هندسی، mesh generator و تشخیص واقعی این روابط در کلاس پایه وجود نداشت.
- `Field` فرزند Quantity بود و geometry اجباری داشت. در این نمونه، نام attribute عمومی
  `geometry` و نمای داخلی آن `_domain` بود؛ نام `domain` بیان ایدهٔ توسعه است و هنوز نام
  نهایی API چنددامنه‌ای محسوب نمی‌شود.
- هویت کمیت با نام و هویت آبجکت domain مشخص می‌شد. شکل ذاتی جداگانه بررسی می‌شد؛ کاربر
  می‌توانست همان کمیت را دوباره تعریف کند، ولی برای همان domain از همان آبجکت geometry
  استفاده می‌کرد. هم‌کلاس‌بودن یا هم‌شکل‌بودن geometryها به معنی یکی‌بودنشان نبود.
- Model یک geometry یا None معرفی می‌کرد؛ Solver و ComputationGraph برای مدل‌های دارای
  geometry، همان آبجکت مشترک را لازم می‌دانستند. این یک بررسی سادهٔ تک‌دامنه‌ای بود؛
  رابطهٔ subset/boundary در اتصال مدل‌ها استفاده نمی‌شد و اعتبارسنجی کامل domain تمام
  Fieldهای ورودی/خروجی هم انجام نمی‌شد.
- domain مشتق از کمیت of گرفته می‌شد. نمودارها نام‌های یکسان روی domainهای متفاوت را با
  برچسب domain از هم متمایز می‌کردند.

این قراردادها نمونهٔ قابل رجوع‌اند، نه الزام به بازگرداندن عین همان inheritance یا همان
محدودیت تک‌دامنه‌ای. ایدهٔ GeoCore چند‌هندسه‌ای مسیر گسترش آن‌هاست.

### ۳. نمایش‌ها، encoderها و اندازه‌های متفاوت

نمونهٔ branch قرارداد Quantity/Value/Signature/Model را نیز داشت: تعریف کمیت از مقدار جدا
بود، شکل ذاتی از محورهای نمونه جدا می‌شد و مدل با امضای ورودی/خروجی، محاسبات نقطه‌ای یا
مصرف کامل یک محور را اعلام می‌کرد. مدل‌ها nn.Module بودند و پارامترهایشان در Solver ثبت
می‌شدند. geometry encoder آموزش‌پذیر می‌تواند در همین الگو representation را بگیرد و
embedding تولید کند؛ وجود GeoCore نباید به معنی انتقال اجباری شبکهٔ encoder به آن بسته باشد.

Value می‌توانست یک Tensor یا لیست تخت Tensorها با محور بیرونی نام‌دار نگه دارد؛ مثلاً
۸ geometry با تعداد رأس/سلول متفاوت. حلقهٔ محور بیرونی و vmap محورهای dense مشترک در Model
وجود داشت؛ دریافت کامل لیست در evaluate نیز ممکن بود. اندازهٔ محورهای هم‌نام به‌صورت
مشترک یا به‌ازای عضو بررسی می‌شد. padding، stacking خودکار، thread/job موازی یا تنسور تو‌در‌تو
وجود نداشت. این بخش، نمایش عددی داده است و به‌تنهایی قرارداد کامل mesh شامل connectivity
و انواع representation را تعیین نمی‌کند.

این قابلیت عمومی لیست و محورهای نام‌دار در main هم باقی مانده است؛ فقط وابستگی معنایی به
Geometry و Field حذف شده است. تصمیم دربارهٔ زمان‌بندی تولید چند mesh و هم‌پوشانی CPU/GPU
را می‌توان روی این پایه توسعه داد؛ branch خودش چنین زمان‌بندی‌ای انجام نمی‌داد.

### ۴. partial derivative با holding دلخواه

درخواست مشتق شامل of، wrt و holding بود. holding یعنی مقدار یک کمیت هنگام همین مشتق ثابت
باشد، حتی اگر خودش تابع wrt باشد؛ این با مشتق معمول نسبت به یکی از چند ورودی مستقل فرق دارد.
ترتیب اعضای holding در هویت درخواست بی‌اثر بود و هر درخواست توقف‌های خودش را داشت.

مثال مشخص:

```text
A(x), B(x), C(x)
D(A, B)
T(D, C)
request: derivative of T wrt x, holding B
```

مسیرهای x → A → D → T و x → C → T در مشتق باقی می‌مانند؛ سهم عبوری از B به تولیدکنندهٔ B
برنمی‌گردد. ثابت‌گرفتن B نباید جد مشترک آن، x، را در مسیرهای دیگر ثابت کند.

این معنا در AD محلی branch پیاده شده بود. هنگام forward، ورودی هر مصرف‌کننده یک view
مستقل می‌گرفت تا مرز ورودی مدل مشخص باشد؛ داده کپی یا detach نمی‌شد و requires_grad متعلق
به کاربر تغییر نمی‌کرد. backward محلی در این مرزها توقف می‌کرد و سیاست wrt/holding هر
درخواست هنگام انتشار سهم‌ها اعمال می‌شد.

holding فقط قاعدهٔ مشتق درخواستی بود، نه قطع آموزش: مقدار B به پارامترهای تولیدکننده‌اش
متصل می‌ماند و loss وابسته به مشتق می‌توانست آن پارامترها را آموزش دهد. شاخه‌های صفر یا
ورودی استفاده‌نشده نیز صفر قابل backward می‌دادند.

### ۵. ساخت و کنترل بخشی از computational graph توسط موتور

ایده این است که موتور در سطح مرز مدل‌ها و عملیات مشتق، گراف وابستگی و مسیر انتشار را خودش
بشناسد و تا حد مفیدی برنامه‌ریزی کند. PyTorch همچنان مشتق محلی عملیات Tensor را حساب می‌کند؛
قرار نیست فرمول backward تمام عملگرهای PyTorch را دوباره بنویسیم.

در نمونهٔ اجرایی:

- ComputationGraph تولیدکنندهٔ کمیت‌ها، ورودی‌های گره، ترتیب اجرا و زیرگراف لازم را نگه می‌داشت.
  درخواست مشتق گرهٔ مجازی بود؛ نمودار Mermaid/DOT نیز همین اتصال‌ها را نشان می‌داد.
- DerivativePlan فقط برای backend مسیرمحور مانند AD ساخته می‌شد: از of به عقب می‌رفت و
  در wrt، holding و ورودی‌های خارجی متوقف می‌شد؛ مدل‌های مسیر و ورودی‌های تابع مشخص بودند.
  depends_on_wrt وابستگی ساختاری را نشان می‌داد، نه تضمین غیرصفر بودن عدد مشتق.
- ForwardTrace ورودی‌های viewشده و خروجی‌های همان forward را برای همان فراخوانی نگه می‌داشت.
  در ترتیب معکوس مدل‌ها، VJP محلی با torch.autograd.grad گرفته و سهم شاخه‌ها جمع می‌شد.
  هیچ forward مدل برای مشتق replay نمی‌شد و tape پایدار میان دو فراخوانی وجود نداشت.
- درخواست‌ها لازم نبود of، wrt یا holding یکسان داشته باشند. adjointهای دارای منشأ عبارتی
  یکسان، VJP محلی را به اشتراک می‌گذاشتند؛ جهت‌های متفاوتِ فعال در مرز مدل گروه‌بندی
  می‌شدند. برابر بودن عددی Tensorها مبنای اشتراک نبود.
- تعداد جهت‌ها با chunk محدود می‌شد؛ اشتراک بین chunkهای متفاوت تضمین نمی‌شد. این روش
  تضمین کمینهٔ مطلق محاسبات یا سرعت بیشتر روی هر سخت‌افزار نبود.

مثال بهینه‌سازی موردنظر: اگر A(C(x)) و B(C(x)) دو خروجی باشند، در شاخهٔ اختصاصی هر کدام
فقط جهت مربوط به همان شاخه محاسبه شود و تازه در C، دو جهت برای عبور از مسیر مشترک گروهی
پردازش شوند. این با دادن batch متراکم شامل جهت‌های صفر به کل گراف تفاوت دارد. نمونهٔ branch
این کنترل را در سطح مدل‌ها انجام می‌داد؛ هر عملیات داخلی Tensor یک گره مستقل در Solver نبود.

گسترش همین ایده برای مرتبه‌های بالاتر می‌تواند محاسبات مشتق را نیز به عملیات داخلیِ قابل
مشتق‌گیری و قابل برنامه‌ریزی تبدیل کند. لازم نیست backwardها Model عمومی باشند، ولی باید
وابستگی و جهت‌های فعالشان برای backend قابل تشخیص باشد. holding هر مرحله مستقل است؛ مثلاً
اگر z=g(x) و T=xz باشد، مشتق اول با holding=z برابر z است و مشتق total بعدی آن g′(x) می‌شود.
این توسعه در branch پیاده نشده بود و صرف داشتن create_graph آن را کامل نمی‌کرد.

### ۶. مرز backendها و قابلیت‌های قابل استفادهٔ مجدد

نمونهٔ branch مسئولیت‌ها را جدا کرده بود: Solver ثبت ماژول و اعتبارسنجی Value را داشت،
ComputationGraph metadata عمومی DAG را نگه می‌داشت، DerivativeEngine درخواست‌ها و گره‌های
مشتق را هماهنگ می‌کرد و AutogradBackend مالک tape، grad mode، بررسی محورهای مستقل و AD بود.
backend، خود Solver را دریافت نمی‌کرد و از گراف و callback اجرای مدل/ذخیرهٔ نتیجه استفاده می‌کرد.

نیاز مقداری هر backend با dependencies اعلام می‌شد. آماده‌سازی اختصاصی با prepare اختیاری
بود؛ metadata آماده‌سازی لزوماً DerivativePlan نبود. FEM یا روش مبتنی بر نمونه‌ها می‌توانست
میدان، مختصات و mesh/connectivity بخواهد و هیچ تحلیل مسیر مدل انجام ندهد. در این نمونه فقط AD
روش built-in بود؛ تست‌های سفارشیِ داده‌محور، جدایی قرارداد از AD را نشان می‌دادند.

محورهای نمونهٔ مستقل هم‌نام برای مشتق متناظر فشرده می‌شدند؛ نام‌های متفاوت، Jacobian صریح
می‌دادند. مصرف کامل محور مشترک در مسیر وابسته به wrt به‌صورت محافظه‌کارانه رد می‌شد؛ مسیر
held یا مستقل از wrt در آن بررسی وارد نمی‌شد. لیست بیرونی و اتصال آموزش نیز پشتیبانی می‌شد.

### ۷. آنچه تجربهٔ branch نشان داد و مسیر توسعهٔ بعدی

در commit محفوظ، ۷۵ تست از جمله holding، شاخه‌های مشترک، گروه‌بندی VJP، ورودی/خروجی برداری،
ragged، آموزش و backend سفارشی پاس شده بودند. مرتبهٔ بالاتر در آن پیاده‌سازی رد می‌شد؛
GeoCore چند‌هندسه‌ای، سازگاری خودکار domainها، FEM آماده و زمان‌بندی موازی وجود نداشتند.
همچنین ثبت گراف با compile برای مسیر عادی، تضمین compile کامل یا سرعت AD محلی نبود.

به‌دلیل هزینهٔ پیچیدگی این مسیر، main فعلاً AD مستقیم و مشتق‌های مرتبهٔ بالاتر را نگه می‌دارد
و Geometry/Field را ندارد. مسیر توسعهٔ شرح‌داده‌شده در این بخش مستقل و قابل بازگشت است:
قرارداد چند domain و domain میدان‌ها، partial با holding، و کنترل هدفمند گراف برای اشتراک
محاسبات می‌توانند بعداً بر پایهٔ تجربهٔ branch پیاده شوند. لازم نیست همهٔ اجزا یک‌جا یا عین
نمونهٔ قبلی بازگردند؛ قابلیت‌های مشترک فعلی مانند Quantity، Value، signature و mesh dependency
نیز نقطهٔ شروع باقی می‌مانند.


## گروه‌بندی وابسته به backend بدون AD محلی — ۲۰۲۶-۱۰-۲۶

به درخواست کاربر، گروه‌بندی به backend واگذار شد. موتور مدل‌های آماده و لازم را اجرا و
درخواست‌های مشتق آماده را با group_key دسته‌بندی می‌کند. compute_group برای هر درخواست
نگاشت وابستگی‌های خودش را می‌گیرد. پیش‌فرض گروه تکی است و compute قبلی معتبر می‌ماند.
prepare_group می‌تواند دادهٔ عددی مشترک، مثل عملگر mesh، را یک‌بار در همان فراخوانی آماده
کند و در مرحلهٔ بعدی با همان کلید دوباره استفاده کند؛ cache پایدار یا DerivativePlan نداریم.

در AutogradBackend، منبع و جهت‌های خروجی یکسان یک reverse sweep با چند target می‌گیرند.
اشتراک فقط of کافی نیست؛ contraction متفاوت روی point/scenario گروه جدا دارد. ofهای متفاوت
با جهت صفر stack نمی‌شوند. خروجی کاهش‌یافته روی لیست می‌تواند targetهای همهٔ عضوها را در
یک sweep بگیرد و خروجی لیستیِ نقطه‌ای فقط targetهای متناظر همان عضو را می‌گیرد. مرتبه‌های
بالاتر به ترتیب وابستگی واقعی اجرا می‌شوند و هر مرحله گروه‌بندی خودش را دارد.

مسیر forward با ورودی/جهت مشترک، روش روی mesh با operator مشترک و Taylor با چند مرتبه از
همین hookها قابل استفاده‌اند. backend می‌تواند dependencies را به ورودی پایه محدود کند،
اگر روش خودش به Value مشتق میانی نیاز ندارد. نمونه‌های تستی JVP، گرادیان P1 مثلثی و مشتق
چندجمله‌ای این قرارداد را اجرا می‌کنند؛ built-in عددی جدید یا پشتیبانی holding اضافه نشد.
جزئیات در [قرارداد گروه‌بندی](derivative_grouping.fa.md) ثبت شده است. این تغییر با ایدهٔ
کنترل گرافِ مدل‌به‌مدل در طرح توسعه فرق دارد و آن را به main بازنمی‌گرداند.

اعتبارسنجی گروه‌بندی: هر ۹۶ تست و اجرای کامل نوت‌بوک دما گذشت. شمارش بازدید گره backward،
کاهش تعداد sweep و جهت‌های تکراری را برای درخواست‌های سازگار تأیید کرد. تست‌های روش‌های
نمونه، جداسازی کلیدهای ناسازگار و استفادهٔ دوبارهٔ آماده‌سازی فقط در همان فراخوانی را بررسی کردند.

## GeoCore wrapper فعلی و آماده‌سازی موازی/RAR در آینده — ۲۰۲۶-۱۰-۲۸

برای رساندن سریع یک مثال به اجرا، مسیر مورد توافق فعلی یک Model wrapper ساده روی GeoCore است؛ خود GeoCore تغییر نمی‌کند. wrapper پارامترهای هندسه را می‌گیرد، محور سناریو را کامل دریافت می‌کند، فعلاً با حلقهٔ ترتیبی روی CPU هندسه و representation/نقاط را می‌سازد و خروجی عددی را به Tensor و Valueهای مناسب موتور تبدیل می‌کند. انتقال به GPU مرحله‌ای جداست؛ Model بودن این wrapper به معنی پشتیبانی محاسبات GeoCore از vmap، torch.compile یا autograd نیست. این بند تصمیم طراحی است، نه اعلام پیاده‌شدن wrapper.

**موضوع موکول‌شده به آینده:** بررسی یک هماهنگ‌کنندهٔ نهایی sampling شبیه DataLoader که تولید سناریو، هندسه و نقاط را ترکیب کند و آماده‌سازی CPU را با workerها و prefetch انجام دهد. امکان هم‌پوشانی تولید batch بعدی با آموزش GPU بررسی شود. هنوز تصمیم نگرفته‌ایم که این هماهنگ‌کننده خود DataLoader باشد یا از آن استفاده کند؛ قرارداد Model فعلی نیز قرار نیست این انتخاب آینده را مسدود کند.

برای RAR، هر دو حالت زیر باز بمانند و در طراحی آینده بررسی شوند:

1. **انتخاب adaptive بیرون workerهای تولید داده:** workerها داده/نقاط کاندید را آماده کنند و انتخاب یا افزودن نقاط بر اساس residual مدل در بخش هماهنگ‌کننده/آموزش انجام شود.
2. **انتخاب adaptive داخل workerها با بازخورد تأخیردار:** residualهای از قبل محاسبه‌شده به workerها داده شوند تا خودشان نمونه‌های بعدی را انتخاب کنند؛ مثال موردنظر، استفاده در step فعلی از residualهای آمادهٔ دو step قبل است. این حالت لزوماً به اجرای مدل یا محاسبهٔ residual در worker نیاز ندارد. residualهای قدیمی باید با نقاط کاندید، سناریو/هندسه و step ارزیابی متناظرشان همراه باشند تا با دادهٔ دیگری اشتباه نشوند.

در حالت دوم، تازگی بازخورد، نحوهٔ انتقال آن به workerها، اثر صف prefetch بر تأخیر واقعی و اثر تأخیر بر کیفیت RAR باید بررسی شوند؛ «دو step» فعلاً مثال سیاست موردنظر است، نه تضمین زمان‌بندی. هیچ‌یک از این دو روش RAR یا هماهنگ‌کنندهٔ DataLoader در این تغییر پیاده‌سازی نشده است.

## پیاده‌سازی رپر GeoCore — ۲۰۲۶-۱۰-۳۱

GeoCoreModel در src/pinn_engine/geocore.py اضافه شد؛ خود GeoCore بدون تغییر باقی ماند. کل محور سناریو ورودی core است، پارامترهای اسکالر با Design.with_params به نسخهٔ مستقل طراحی تبدیل می‌شوند و ساخت representation با حلقه روی CPU انجام می‌شود. هر پنج representation و collocation از یک کلاس با نگاشت outputs به Quantityهای کاربر پشتیبانی می‌شوند. محور اول خروجی‌ها لیستی است و نامش به scenario_axis وابسته است؛ محورهای داخلی پیش‌فرض صریح‌اند و با output_axes قابل تغییرند. edge_index و کانال‌های voxel برای قرارداد ابعاد ذاتیِ انتهایی جابه‌جا می‌شوند. ورودی CUDA یا نیازمند گرادیان پذیرفته نیست؛ هیچ مشتق‌پذیری از ساخت هندسه ادعا نمی‌شود. seed تعیین‌شده تکرارپذیر و None تازه است. آماده‌سازی موازی، prefetch و هر دو حالت RAR همچنان تصمیم‌های آینده‌اند. جزئیات نصب و محدودیت‌ها در [رپر GeoCore](geocore.fa.md) ثبت شده‌اند.

## قرارداد تبدیل Neural3DBench به Model — ۲۰۲۶-۱۰-۳۱

تصمیم طراحی در زمان ثبت؛ اکنون طبق بخش پیاده‌سازی پایین، شبکه‌ها Model موتور شده‌اند:

- هر شبکه subclass جداگانهٔ Model می‌شود؛ منطق عددی داخلی حفظ می‌شود و نیازی به adapter مستقل برای هر فراخوانی نیست. init تنظیمات معماری موجود را در config می‌گیرد و دو نگاشت inputs و outputs را دریافت می‌کند: نام نقش ورودی/خروجی در شبکه به Quantity انتخابی کاربر. اسم Quantityها دیگر به نام‌های ModelInput محدود نیست؛ مثلاً inputs={"coordinates": wing_points} و outputs={"latent": wing_embedding}.
- ورودی‌های الزامی باید در inputs باشند. حضور ورودی‌های اختیاری در همین نگاشت هنگام ساخت instance قرارداد آن را تعیین می‌کند؛ اگر انتخاب شدند هنگام اجرا مقدارشان لازم است، وگرنه از Signature حذف می‌شوند. نگاشت باید با config سازگار باشد؛ مثلاً تعداد ویژگی‌های غیرصفر، point_features را اجباری می‌کند. کلیدهای ناشناخته یا ورودیِ استفاده‌نشده نباید بی‌صدا پذیرفته شوند. گزینه‌های تکراری مانند use_point_mask و use_query_coordinates برای بیان همان حضور لازم نیستند.
- outputs غیرخالی، مشخص و ثابت است؛ فقط خروجی‌های عددی پشتیبانی‌شده مانند predictions و latent قابل انتخاب‌اند. نام، شکل ذاتی و هویت Quantity خروجی را کاربر تعیین می‌کند. محور/محورهای مؤلفهٔ عددی به شکل Quantity تبدیل شوند، با حفظ همهٔ محورهای نمونه؛ مثلاً ۱ مؤلفه به () و ۹ مؤلفه به (3,3). تعداد مؤلفه‌های ناسازگار باید خطا بدهد. معنای latent و Signature برای هر subclass جداست و از نام خروجی حدس زده نمی‌شود.
- کد auxiliary و metadata در شبکه‌های اصلی حفظ شود؛ فعلاً به‌عنوان خروجی موتور انتخاب‌پذیر نیستند. نبود یک قابلیت، مثل latent در GCN فعلی، باید در انتخاب خروجی خطا بدهد.
- **الزام برای زمان افزودن domain:** سازگاری domain کمیت‌های ورودی و خروجی هر شبکه بررسی شود؛ در حالت تک‌دامنه‌ای موردنظر، domain ورودی‌ها و خروجی‌های مکانی باید یکی باشد. کمیت‌های غیرمکانی مانند embedding لزوماً domain ندارند و نباید صرفاً به این دلیل رد شوند. قرارداد دقیق اعتبارسنجی با طراحی domain تعیین می‌شود؛ برابر بودن نام یا shape جای بررسی domain را نمی‌گیرد.
- قرارداد محورهای کامل و batch در هر شبکه جدا تعریف شود. normalization="none" اکنون در PointNet و PointNet++ قابل انتخاب است، ولی پیش‌فرض upstream همچنان batch است؛ سیاست پیش‌فرض موتور و پشتیبانی training با BatchNorm در batching خودکار نباید بی‌صدا حدس زده شود. مشتق تخصصی، RAR و خروجی‌های ساختاریافته پیش‌نیاز آغاز تبدیل شبکه‌ها نیستند.

## اصلاح استقلال محورها و Signature با ... — ۲۰۲۶-۱۰-۳۱

طبق تصمیم صریح کاربر، حفظ نام هر محور ورودی در خروجی مدل، تضمین استقلال نمونه‌ها روی آن محور است؛ این تصمیم جایگزین رفتار قبلی می‌شود که core مصرف‌شده را مستقل فرض نمی‌کرد. backend AD اکنون محورهای حذف/تغییرنام‌یافته را در مسیر وابسته دنبال می‌کند؛ اگر پس از reduction یا اختلاط نام سابق دوباره ظاهر شود، مشتق متناظر همچنان رد می‌شود. مدلِ مخلوط‌کنندهٔ نقاط باید محور خروجی را تغییر نام دهد. engine نمی‌تواند راست‌بودن ادعای استقلال یک تابع دلخواه را از درون evaluate اثبات کند.

حالت نیمه‌تمام all_axes=True کنار گذاشته شد و وارد API نشد. رشتهٔ "..." در نگاشت‌های inputs و outputs گروه محورهای باقی‌مانده را معرفی می‌کند. Signature دارای wildcard باعث تحویل مستقیم و یکبارهٔ Valueها به evaluate می‌شود؛ خود مدل نتیجه را با Value و محورهای واقعی برمی‌گرداند. حفظ "..." در خروجی، گروه را با تضمین استقلال حفظ می‌کند؛ نبودش یعنی تجمیع آن گروه. شکل Quantity، ترتیب/طول محورها و نوع خروجی همچنان بررسی می‌شوند. مسیر امضای معمولی همچنان Tensor/list و batching خودکار دارد. Solver تغییر اجرایی لازم نداشت؛ مستندات و تست‌های قدیمیِ استقلال به قرارداد جدید اصلاح شدند. جزئیات در [راهنمای Signature](signature.fa.md) است.

## independence صریح و توقف AD روی مسیر وابسته — ۲۰۲۶-۱۰-۳۱

Signature ورودی اختیاری independence از نوع dict[str,bool] می‌گیرد. مقدار پیش‌فرض محورهای مشترک در post_init به True تکمیل می‌شود؛ قانون False برای محور مشخص و برای گروه "..." مجاز است. نام صریح بر قانون گروه اولویت دارد و گروه هنگام اجرا به نام‌های واقعی محورها باز می‌شود، بدون تغییر قرارداد ثابت مدل. در نتیجه حفظ نام محور دیگر مجبور نیست به معنی استقلال باشد؛ فقط پیش‌فرض آن است. این تصمیم جایگزین بخش مربوط به اجبار تغییر نام برای پردازش وابسته در یادداشت قبلی است.

طبق تصمیم کاربر، فعلاً اگر حتی یک بخش از مسیر وابسته به wrt تا of برای یک محور استقلال را تضمین نکند، AD با نام محورهای وابسته و درخواست مشتق خطا می‌دهد؛ True در ادامه مسیر وابستگی قبلی را پاک نمی‌کند. مسیر نامرتبط باعث خطا نمی‌شود. اجرای عادی و loss.backward آموزش محدود نیستند. برای قانون False، پشتیبانی عددی جدید از Jacobian کامل اضافه نشده است؛ قرارداد خروجی دو نقش محور هم‌نام هنوز باز است.

برای آینده: بررسی پشتیبانی از Jacobian حالت وابسته، با حفظ روش فشردهٔ حالت مستقل و جلوگیری از کار اضافه در شاخهٔ مستقل. در ترکیب A(x)+B(x)، اگر A وابسته و B مستقل باشد، صرف محاسبهٔ Jacobian کامل خروجی با autograd مستقیم ممکن است جهت‌های کامل را از B هم عبور دهد. metadata برای تشخیص کافی است ولی بهینه‌سازی عددی نیازمند استفادهٔ واقعی از ساختار شاخه‌ها، روش تخصصی یا AD مناسب است. تضمین حذف تمام اضافه‌کاری با backend فعلی یا compile داده نمی‌شود. فعلاً توقف صریح AD جای این پیاده‌سازی پیچیده‌تر را می‌گیرد. Jacobianهای قبلاً پشتیبانی‌شده با نام محورهای متمایز و بدون قانون False مسدودکننده حفظ شده‌اند. جزئیات در [راهنمای Signature](signature.fa.md) آمده است.

## پیاده‌سازی شبکه‌های Neural3DBench — ۲۰۲۶-۱۰-۳۱

هر ۱۱ شبکه مستقیماً از Model ارث می‌برند و constructorهایشان config، inputs و outputs می‌گیرند. سورس عددی همان‌جا در third_party نگه داشته و با نام pinn_engine.networks نصب می‌شود. پارامترها و نام‌های state_dict حفظ شده‌اند؛ predict(ModelInput) دسترسی به خروجی‌های قبلیِ ساختاریافته/auxiliary/metadata را نگه می‌دارد، ولی forward قرارداد Value موتور را دارد. نگاشت نقش‌ها، تعداد مؤلفه‌ها و حضور ورودی‌های اختیاری هنگام ساخت بررسی می‌شود.

وجود واقعی BatchNorm در زیرماژول‌ها باعث Signature با پیشوند ... برای تمام ورودی/خروجی‌هاست. کل batch داخل evaluate مدیریت می‌شود؛ اگر BatchNorm از آمار batch استفاده کند independence گروه False و با آمار ثابت eval برابر True است. شبکه‌های GCN/GAT/MeshGraphNet حتی بدون BatchNorm کل batch را می‌گیرند و با offset یال‌ها، گراف‌های جدا از هم را در یک اجرای شبکه پردازش می‌کنند. سایر شبکه‌ها ... ندارند و از vmap/حلقهٔ لیستی موتور استفاده می‌کنند. Dropout روی محورهای mapped مستقل می‌کشد. وابستگی point/spatial/vertex هر شبکه صریح اعلام شده و AD فعلی روی محور مشترکِ وابسته طبق قرارداد خطا می‌دهد؛ آموزش معمولی برقرار است.

لیست‌ها padding نمی‌شوند؛ BatchNorm آمار batch با اندازهٔ متفاوت core خطا می‌دهد تا آمارش بی‌صدا عوض نشود. ماسک ورودیِ خود شبکه آمار BatchNorm را ماسک نمی‌کند. GINO برای vmap از ماسک با طول ثابت استفاده می‌کند و در مسیر Model، activation checkpoint خاموش است؛ در predict روشن باقی می‌ماند. کاهش حافظه و حذف headهای خروجیِ انتخاب‌نشده، compile کامل و سنجش GPU جزو این پیاده‌سازی نیستند. قرارداد domain و بررسی برابر بودن domain ورودی/خروجی مکانی همچنان باید زمان افزودن domain پیاده شود. جزئیات محورهای latent و محدودیت‌ها در [راهنمای شبکه‌ها](networks.fa.md) آمده است.

## checkpoint بیرون batching برای GINO — ۲۰۲۶-۱۰-۳۱

خاموش‌بودن checkpoint در مسیر Modelِ GINO در بند قبلی جایگزین شد: Model پس از ساخت تمام vmapهای لازم، کل تابع batch‌شده را با checkpoint(..., use_reentrant=False) اجرا می‌کند. checkpoint داخلی kernel در evaluate همچنان خاموش است تا داخل vmap قرار نگیرد؛ مسیر predict(ModelInput) checkpoint داخلی قبلی را نگه می‌دارد. checkpoint_batches پیش‌فرض Model برابر False و فقط برای GINO برابر True است؛ با False روی instance می‌توان اجرای مرجع گرفت. در no_grad کنار گذاشته می‌شود، در لیست ragged برای هر عضو جدا اجرا می‌شود و مسیر wildcard این گزینه را اعمال نمی‌کند.

تبادل حافظه با محاسبهٔ مجدد اکنون روی کل فراخوانی عددی انجام می‌شود؛ کاهش tensorهای ذخیره‌شده برای backward تست شده ولی benchmark سرعت یا peak حافظهٔ GPU انجام نشده است. replay نباید بی‌قید برای مدل‌هایی با تغییر state مثل آمار BatchNorm فعال شود. تست‌ها شامل batch چندمحوره، ragged و بدون batch، مشتق‌های تا مرتبهٔ سوم، queryهای مستقل در Solver با دو اندازهٔ chunk مشتق و backward از loss شامل مشتق مرتبهٔ سوم هستند؛ خروجی و گرادیان پارامترها با checkpoint خاموش مقایسه می‌شوند.


## ساختار یکپارچهٔ src — ۲۰۲۶-۱۰-۳۱

GeoCore به صورت پکیج مستقل به src/geocore منتقل شد و import geocore حفظ شد. شبکه‌های همکاران با نام عمومی‌تر pinn_engine.networks در src/pinn_engine/networks قرار گرفتند و helper قراردادشان از ریشهٔ موتور به networks/_contract.py منتقل شد. نام neural3dbench فقط برای provenance/فایل‌های مرجع باقی می‌ماند؛ import اجرایی قدیمی به pinn_engine.networks تغییر کرده است. اسناد جاری در docs/networks.fa.md هستند.

setuptools اکنون پکیج‌ها را مستقیماً از src پیدا می‌کند و mapping ویژه به third_party حذف شد. یک نصب ریشه هر دو پکیج را ارائه می‌کند؛ dependencyهای عددی geometry اختیاری‌اند و با extra geometry نصب می‌شوند. ## نرمال‌سازی مشترک و BatchNorm لیستی — ۲۰۲۶-۱۰-۳۱

منطق BatchNorm Tensor/list/mask به pinn_engine/normalization.py منتقل شد. آمار مشترک از نمونه‌های واقعی با وزن برابر هر نقطه می‌آید و running statistics یک‌بار در فراخوانی به‌روز می‌شود. قرارداد ragged قبلی برای PointNet/PointNet++ جایگزین شد: adapter بیرونی padding داخلی می‌سازد، mask از طریق context محدود به همان فراخوانی به normalization می‌رسد، و پس از اجرای یکبارهٔ شبکه خروجی به لیست اولیه برمی‌گردد. انتخاب padding برای حفظ بدنهٔ اصلی شبکه و کم‌بودن تغییرات است و هزینهٔ محاسبات/حافظهٔ آن حذف نشده است. شبکه‌های grid به adapter مستقل نیاز دارند و این تغییر ادعای پشتیبانی ragged کامل آن‌ها را ندارد.

طبق تأیید کاربر، PointNet گزینهٔ instance را برای نرمال‌سازی فقط روی point دارد؛ بعد از pooling در این حالت normalization نداریم. BatchNorm پیش‌فرض قبلی و حالت none حفظ شده‌اند. استقلال point همچنان False و استقلال batch برای instance برقرار است. ماسک صریح PointNet/PointNet++ اکنون آمار normalization را هم محدود می‌کند؛ این رفتار جدید است. محتوای عددی encoder، T-Net، headها و بلوک‌های اصلی در گزارش تطبیق با منبع بررسی شده و تغییرات واقعی رابط/vmap/normalization جدا ثبت شده‌اند؛ ادعا نمی‌شود که پشتیبانی ragged از قبل در کد همکار بوده است.
